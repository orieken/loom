# Build the runner images — Debian and UBI9

A prompt for building the two browser-runner images: one image definition with two supported
variants, for running Playwright (and Cucumber) suites in real Chrome and Edge under a virtual
display, with working WebGL and an optional VNC viewer. Written for Saturday, and meant to be
reusable in any repository whose tests need a real browser: testing-with-certs, or a team at work.

**Scope: build, verify and document both images.** Debian first; UBI9 only once Debian passes
every check below.

## The contract both variants meet

Every item applies to `debian` and `ubi9` alike. A variant ships only when all of them hold.

**Reproducible**
- The base image is pinned by digest. Never a tag alone, never `latest`.
- Every installed system package is pinned to an exact version in a lock file (`apt.lock`,
  `rpm.lock`), generated by `lock-packages.sh [--ubi9]` from a short, hand-edited
  `packages.list` / `packages.ubi9.list`. Lock files are never edited by hand.
- The build fails, and says which package, when a locked version is unavailable. Browser vendors
  drop old versions from their indexes; the fix is to regenerate the lock, never to unpin.
- Node, pnpm and Playwright versions match the repository: pnpm from `packageManager` in the root
  `package.json` if set, otherwise one pinned version stated in the Containerfile; Playwright's
  ffmpeg from the same Playwright version as `@playwright/test` in the lockfile.

**Verified**
- Google's and Microsoft's signing keys are vendored in `keys/`, and the build checks them against
  `keys/SHA256SUMS` (`sha256sum -c`) **before** importing them. Fetching a key at build time is
  not acceptable.
- Every repository is signature-checked. No `gpgcheck=0`, `--nogpgcheck`, `--allow-unauthenticated`,
  `[trusted=yes]`, or `rpm -e --nodeps`.
- Repository URLs use `https://`.
- No `curl | bash`, no installer scripts from the network, nothing downloaded without a checksum.

**Safe to run**
- Runs as uid 1000 (`runner`, `HOME=/home/runner`). On the Node base image, rename the existing
  uid 1000 `node` user rather than adding a second one.
- The repository is mounted at `/work` at run time, never copied in. No `COPY . .`. A named volume
  holds the pnpm store.
- With `RUNNER_VIEWER` unset, nothing listens on any port.
- With `RUNNER_VIEWER=1`: x11vnc with a random password, bound to localhost; noVNC on 6080 bound to
  127.0.0.1; the password written to a file only the runner user can read, and its path printed.
  Never the password itself in logs.

**Honest**
- The entrypoint starts Xvfb (`:99`, 1920x1080x24, `-nolisten tcp`), waits until `xdpyinfo` succeeds
  (fails after 15 seconds, with a message), starts openbox, optionally the viewer, and ends with
  `exec "$@"`. The container's exit code is the command's. No supervisord.
- `runner-check`, baked into the image, launches Chrome and Edge **headed**, creates a `webgl2`
  context in each, and writes to `/work/evidence/`: the WebGL renderer per browser, the browser
  versions, and the installed package list. It exits non-zero if either browser has no context.
- WebGL works through ANGLE's SwiftShader backend: Chrome headed under Xvfb, launched with
  `--use-gl=angle --use-angle=swiftshader`. `runner-check` and every suite's Chrome project use
  those same args. Mesa llvmpipe is **not** the renderer: in the first debian build, headed Chrome
  with no GL args, with `--use-gl=desktop`, and with `--use-angle=gl` all got a null `webgl2`
  context. Install the Mesa packages anyway (Chrome's GL probing touches them). Do not rely on
  new-headless Chrome's implicit SwiftShader fallback; it needs `--enable-unsafe-swiftshader` now.
  Record the renderer string `runner-check` reports; it should name SwiftShader.

## Variant specifics

### `debian` (default; everyday use, CI, the factory)

- Base: `node:24.19.0-bookworm-slim` at the digest in `docs/runner-image.md`.
- Packages, at least: Chrome and Edge stable, `xvfb`, `x11-utils`, `openbox`, `x11vnc`, `novnc`,
  `python3-websockify`, `libgl1-mesa-dri`, `libegl1`, `libgles2`, `dbus`, `dbus-x11`, `fontconfig`,
  `fonts-liberation`, `fonts-noto-color-emoji`, `procps`, `ca-certificates`.
- The packages that bootstrap key import (`ca-certificates`, `gnupg`) are pinned too: install them
  from the lock in the first step, not with a bare `apt-get install`.
- Pattern to copy: testing-with-certs `install-packages.sh` (key checksums, apt timeouts, every
  package from the lock in one install).

### `ubi9` (teams that need a Red Hat base, FIPS, or Red Hat errata)

- Base: `registry.access.redhat.com/ubi9/ubi` pinned by digest; Node copied from the pinned Node
  image's binary, as testing-with-certs does.
- Repositories, from `docs/runner-image.md`, "The UBI9 variant":
  - UBI for everything it has, with `excludepkgs=mesa*`;
  - CentOS Stream 9 BaseOS, AppStream and CRB for Xvfb and **all** Mesa packages (including
    `mesa-dri-drivers`, which UBI lacks and Chrome's GL probing needs), with `excludepkgs=openssl*` so UBI's
    FIPS OpenSSL stays;
  - EPEL 9 only for `x11vnc`, `openbox`, `novnc`, `python3-websockify`. EPEL keeps only the
    latest build, so these four RPMs are vendored in `rpms/`, checked against `rpms/SHA256SUMS`
    and EPEL's signing key, and installed from there.
- `xorg-x11-utils` for `xdpyinfo` (testing-with-certs' first live test caught it missing).
- The same entrypoint, `runner-check` and evidence as `debian`, byte for byte where possible.
- Say plainly in the docs what it does not give: the display, viewer and Mesa packages come from
  Stream and EPEL, which Red Hat does not support. It is a compliance choice, not a more locked
  down image.

## Gaps found in the first attempt (fix these first)

The factory's first developer run (2026-10-30) got most of the design right and missed these:

1. The vendored keys are imported without checking `keys/SHA256SUMS`.
2. Chrome's apt source uses `http://dl.google.com`.
3. `ca-certificates gnupg` are installed unpinned before the lock is applied.
4. ffmpeg comes from `npx --yes playwright@1.57.0`, which fetches Playwright at build time; take
   the version from the lockfile and fail if they differ.
5. pnpm is pinned in the Containerfile but not checked against the repository.

## Per repository

Only these change between repositories:

- the image name and tag;
- extra layers on top: testing-with-certs adds `trust.sh`, NSS tools and managed browser policies
  `FROM` either variant, in its own repository;
- the run script (`scripts/ui-suite-in-chrome.sh` in Saturday): how the app and its mocks start, the
  health URL, and which Playwright project runs;
- `.dockerignore`: check that nothing the tests import is excluded (Saturday's bare `lib` pattern
  excluded the app's site classes).

## Verify

Run each on the variant being built. Record the output in the delivery notes.

```bash
docker build --platform linux/amd64 --target debian -t saturday-runner:debian containers/saturday-runner
docker run --rm saturday-runner:debian true; echo "exit=$?"                 # 0
docker run --rm saturday-runner:debian false; echo "exit=$?"                # 1: exit codes pass through
docker run --rm -v "$PWD:/work" saturday-runner:debian runner-check        # renderer recorded, exit 0
docker run --rm saturday-runner:debian id -u                                # 1000
docker run --rm saturday-runner:debian sh -c 'ss -ltn | tail -n +2 | wc -l' # 0: no listeners
docker run --rm -e RUNNER_VIEWER=1 saturday-runner:debian sh -c 'sleep 3; ss -ltn'  # 127.0.0.1:5900 and :6080 only
grep -nE 'gpgcheck=0|nogpgcheck|trusted=yes|curl[^|]*\| *(ba)?sh|COPY \. \.|supervisord|http://' containers/saturday-runner/Containerfile*   # nothing
scripts/ui-suite-in-chrome.sh                                               # suite green, report in artifacts/ui-suite/
```

And the negative checks, which prove the checks themselves can fail:

- Corrupt one byte of `keys/google.asc`: the build fails at the checksum step.
- Change one version in the lock to one that does not exist: the build fails naming that package.
- Run the WebGL spec with `--disable-gpu --disable-software-rasterizer`: it fails.

Repeat for `--target ubi9`.

## Time

Under amd64 emulation on Apple Silicon, a cold build takes tens of minutes, and generating a lock
takes longer. Do the build-and-lock work outside any step with a 30-minute limit. Loom's stages have
one (roadmap L3.78): run this prompt directly in Claude Code, or on native Linux.
