## Schema Changes

- No relational or document database is involved in this feature. There is no `Table Name` to list.
- `ImplementationState` (JSON document, `shared/schemas/pipeline/implementation.schema.json`)
  - `ADDED filesDeleted (array of string, optional, omitempty)` — new path-naming field; a rename is encoded as the new path in the existing `filesCreated` and the old path in this new `filesDeleted`.
- `QAState` (JSON document, `shared/schemas/pipeline/qa.schema.json`)
  - `ADDED testFilesDeleted (array of string, optional, omitempty)` — same convention as above, scoped to QA's test-file claims.
- `SecurityState` — no field addition. It gains a validation rule only (rejecting `" -> "` in its existing `filesModified`), not a new property, so its schema is unchanged by this feature.

These are JSON Schema documents describing typed pipeline-state artifacts (`internal/state/*.go` structs serialized to JSON and validated by schema), not a database table. I'm reviewing them under this contract because they are the closest thing this feature has to a "schema," and because `shared/schemas/pipeline/*.json` are generated artifacts this process should still check for additive-only, non-breaking change.

## Migration Strategy

- **Phase**: Safe Addition
- **Details**: There is no database and no migration script. The two schema files are regenerated by `go run ./cmd/gen-schemas` directly from the updated Go struct tags (`FilesDeleted []string \`json:"filesDeleted,omitempty"\`` and `TestFilesDeleted []string \`json:"testFilesDeleted,omitempty"\``) — never hand-edited. Both new properties are optional with `omitempty`, so:
  - No existing field is removed, renamed, or made required.
  - Every previously-valid `implementation.json` / `qa.json` document continues to validate unchanged, with no default-value backfill needed, because absence of the field is itself the valid prior state.
  - There is no "old consumer / new consumer" window to manage with dual-writes — this isn't a stored, mutable record with readers and writers on different deploys. Each pipeline run produces its own state document fresh, consumed once by the orchestrator's claim checker in the same run. There is nothing to backfill and nothing that stays half-migrated.
  - This is why "Safe Addition" rather than "Expand" is the correct phase label: Expand/Contract exists to manage a column that is read and written by code that deploys at different times against data that persists across those deploys. Neither condition holds here — the "schema" is a per-run artifact, not persistent storage.
- A genuine future **Contract** phase would only arise if `filesCreated`/`filesModified`/`filesDeleted` were ever consolidated into a single tagged-union field — out of scope for this feature and not proposed by architecture-notes.md.

## Developer Handoff Notes

- Do not hand-edit either `.json` schema file. Change the Go struct tags in `internal/state/implementation_state.go` and `internal/state/qa_state.go`, then run `go run ./cmd/gen-schemas` from the repo root and commit only the regenerated files under `shared/schemas/pipeline/`.
- Keep both new fields `omitempty` on the Go struct and optional (not `required`) in the generated schema — this is what makes every existing state document validate unchanged, per the feature's own acceptance criteria. Do not add a schema-level default value; absence of the array is the correct "nothing was deleted" representation, not an empty-array default.
- There is no query-performance, indexing, N+1, or DataLoader concern on this feature — there is no database read/write path at all. The "claim verification" the architecture notes describe (`internal/orchestrator/claims.go` checking `filesDeleted` against the filesystem and `WorkTree.ChangedPaths()`) is a filesystem/git-status check, not a data-access pattern, and is correctly scoped to the architect/developer stages rather than this one.
- The one place this feature touches anything resembling "persisted state" is the git worktree itself (via the existing `WorkTree.ChangedPaths()` / `git status --porcelain`), and architecture-notes.md already directs that no new `WorkTree` method or interface change is needed or in scope — I have nothing to add on top of that; don't introduce a cache, index, or storage layer for posture data, the existing porcelain-output read is sufficient and is outside this feature's change set.
- If a future feature ever needs `filesDeleted`/`testFilesDeleted` history to persist across runs (e.g., for a dashboard or audit trail), that would be a genuine new persistence requirement and should come back through data-engineer as its own feature — don't improvise a storage mechanism as part of this one.
